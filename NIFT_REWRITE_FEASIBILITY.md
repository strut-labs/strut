# CP110 — Nift rewrite feasibility

## Purpose

This checkpoint asks whether rewriting Nift in Strut would improve either project. It is not a self-hosting trophy exercise.

## Nift capabilities mapped to current Strut

| Nift requirement | Current Strut status | Notes |
| --- | --- | --- |
| Filesystem traversal/read/write | Available | Filesystem and stream APIs are implemented. |
| JSON project/tracking metadata | Available | Built-in `json` uses JSONIC. |
| Fast numeric/config parsing | Available | Compiler/runtime prefer `from_chars` where suitable; JSONIC handles JSON numbers. |
| Process execution | Available | `exec` plus child processes/pipes. |
| Threads/concurrency | Available | Native threads, mutexes, channels, async executor. |
| HTTP/networking | Available | TCP, TLS client and HTTP client/server surfaces exist. |
| SQLite | Available | System/external SQLite integration exists. |
| Incremental dependency metadata | Available | Strut's own `.info.json` object metadata was deliberately informed by Nift's model. |
| Native/static/dynamic linking | Available | Supported by the bootstrap backend. |
| Cross-platform paths/toolchains | Designed/partially certified | Linux is locally exercised; macOS/Windows await CI runners. |
| Mature parser/template engine | Not equivalent yet | Strut can implement it, but Nift's production parser/template behaviour is much more battle-tested. |
| Dynamic JSON collection ergonomics | Incomplete | The prototype exposed that a JSON array obtained through dynamic indexing does not yet provide the same convenient collection surface as native arrays. |
| Proven performance parity | Unknown | Requires equivalent Nift workloads, profiling and optimisation rather than inference from microbenchmarks. |
| Mature distribution/release coverage | Incomplete | Platform certification and release-candidate checkpoints remain open. |

## Prototype: Nift page-info reader

`dogfood/nift-info/main.p` reads a real Nift `.info.json` file with `ifstream`, parses it with Strut's built-in JSON/JSONIC integration, and reports the page name, content path, output path and dependency list.

The prototype was run against the Strut website's real `.nift/public/index.info.json` generated by Nift.

Observed development-host baseline for this prototype:

- bootstrap compile/link: about 2.73 s;
- produced debug executable: about 1.30 MB;
- runtime RSS reported by `/usr/bin/time`: about 1.8 MiB;
- runtime completed below the timer's 0.01 s resolution.

These figures are a local feasibility baseline, not a comparison with Nift and not a public performance claim.

## What the prototype taught us

The required file/stream and JSON primitives are already usable. It also exposed a real API gap: `info["dependencies"]` is a dynamic JSON value and currently cannot simply use `.size()` like a native Strut collection. The prototype therefore stringifies that array rather than pretending the ergonomic gap does not exist.

That is exactly the kind of dogfood feedback that should be resolved before attempting a large rewrite.

## Decision

Do **not** rewrite Nift yet.

Strut now has enough systems capability that a future rewrite is technically plausible, but the evidence does not yet justify replacing a mature C++ Nift implementation. Revisit after:

1. macOS and Windows certification are green;
2. Strut has been used for larger real programs;
3. JSON/dynamic-data ergonomics have been improved through dogfooding;
4. equivalent Nift workloads have been benchmarked and profiled;
5. the rewrite offers measurable maintenance, safety, deployment or performance benefits.

Nift remains a valuable reference implementation and future dogfood target, not a mandatory milestone for Strut's first release.
